Everything in this series so far has stayed inside one head (my own) and one workspace. The skills, scripts, instruction files and decision records I have written about are the durable things a single engineer accumulates while working with an agent, and the point each time was getting good work out of myself and the agent and onto disk where it would survive the session. Sooner or later one of those artefacts needs to reach beyond the repo it was born in. A skill that saves me an afternoon saves a colleague the same afternoon, and one that captures how we do something properly is wasted if only I ever run it. So this time I am getting the work out to the rest of the team: where a shared skill should live, how it travels there, and how a collection of them stays current rather than quietly rotting once more than one person leans on it.

## Where a shared skill belongs

The decision about where a skill should live comes down to where it is relevant rather than whether it can be reused. Some skills are bound tightly to one project, the knowledge of how to deploy this particular system, or how an expert agent for this particular codebase ought to behave, and that knowledge is nobody else's business, so it stays in the project repository and travels with it. Other skills have nothing to do with any one project at all. A skill that applies our branding, or crops a batch of screenshots to a consistent region, or knows the house format for an engineering plan, is the kind of thing every project will want, and that belongs somewhere the whole organisation can reach it, in a shared plugin marketplace rather than any single repo. Skills are only one of the things a plugin can carry. The same packaging distributes agents, hooks, MCP servers and more, so everything that follows about where something belongs, how it travels, and how it stays current applies to all of them, and I lean on skills as the running example only because they are what I reach for most.

If that gradient sounds familiar, it is the same one I described in [Tending the Context](/notes/tending-the-context), where a `CLAUDE.md` file grows more specific the deeper in the tree it sits, and context-specific rules load only when I open the Java files or the crypto code they apply to. Skills are a coarser-grained version of the same idea, where context should live as close as possible to where it is used and move up to a wider scope only as it proves more generally applicable. I picked that principle up from a piece called [*How We Made Our Monorepo Ergonomic for Agents*](https://www.getbasis.ai/blogs/how-we-made-our-monorepo-ergonomic-for-agents), which calls it localisation, and it answers the marketplace-or-repo question more or less on its own.

## How a skill travels, and when it graduates

Getting a skill into the shared marketplace is itself a small piece of work that recurs, so naturally it became a skill of its own, one whose only job is to help another skill find its way into the catalogue where everyone can select it. There is a neat circularity in that, and it is exactly the move the rest of this series has been making, where any workflow worth repeating eventually gets written down as something an agent can run, sometimes as a skill and sometimes as one of the deterministic scripts I wrote about in [Determinism and Useful Ambiguity](/notes/determinism-and-useful-ambiguity).

The harder question is when a skill should graduate from one project up to that shared home, and the answer is that I try not to rush it. The instinct is the same rule of three from [Skills as a By-product of Doing the Work](/notes/skills-as-a-by-product-of-doing-the-work), one level up, where I do not pull a shared abstraction out the first time I notice a pattern, but wait until the repetition is real and has proved itself across a few places. A skill promoted too early is just a premature abstraction wearing a different hat, so the sensible default is to let a useful thing sit in one project for a while, and only reach for promotion once I catch myself doing the same thing over and over across everything I build.

Some of that graduation does not climb all the way to the marketplace, but settles at a middle layer we call a vine. A vine is the top-level workspace for a project that spans several repositories, a spine that holds the cross-cutting things belonging to no single component, the system architecture, the decision records, the cross-repo plans, the operational runbooks, and the shared agent context. It is deliberately not a monorepo, since each component stays an independent repository cloned underneath it, and a bootstrap step assembles them into one workspace so that an agent (or a new engineer) can open the whole project at once and get oriented quickly. The decision records inside a vine follow the same localisation rule from earlier, with system-wide decisions kept at the top and component-specific ones living next to the code they govern, so the structure of the workspace physically enacts the principle that decides where a skill belongs.

A vine starts life from a GitLab project template, and templates have an awkward property worth drawing out. A new project gets a copy of the template at creation rather than a clone, so there is no link back afterwards and no upstream to pull from, which means any improvement made to the template later never reaches the projects already created from it. That shapes how we treat it. The template is kept deliberately lean, carrying almost nothing beyond a single skill that helps an agent understand the vine layout itself, and the bar for adding anything new is high, roughly whether the thing is certain to be wanted by every current and future project rather than merely useful to one or two of them. The same instinct to scrutinise anything that loads by default, and to make every included line justify the space it takes, runs right through this, and it is why a copy-on-creation template has to stay spartan.

## Keeping the collection current

A shared skill that has drifted out of date is worse than no skill at all, because people trust it and act on it, so the harder half of distribution is keeping the collection current once it is out of my hands. Two mechanics carry most of it, and they pull in opposite directions for good reasons.

The first guards against a quiet failure I had not anticipated. When I install one of these plugins, the harness (Claude Code) copies its files into a cache on my own disk, and that cache is what the agent reads, so an agent asked to improve a skill will by default edit the cached copy. The improvement then sits trapped on one machine, helping nobody else, and it is silently overwritten the next time the marketplace updates. It feels productive, because the skill is better on my laptop, and it is the distribution equivalent of fixing a bug in my local checkout and never pushing it. The solution is a contribute workflow that refuses to touch the cache at all and instead drives the change upstream, cloning the canonical repository, branching, editing the real `SKILL.md`, running the validator, committing with a why-focused message, and opening a merge request. Turning a private tweak into a shared one is the whole point of it, and in practice it works.

That is how the marketplace converges, with one canonical source that everyone pulls from and contributes back to, so the collection cannot splinter into a dozen personal variants each rotting in its own direction. A vine works the opposite way. Because it begins as a copy with no upstream, a vine is expected to diverge from its template the moment a project is born, picking up project-specific skills and structure as it goes, and that divergence is the intended behaviour rather than a fault. The aim in both cases is to avoid a landscape of stale half-copies, and the method is reversed depending on the kind of artefact, so I fight divergence hard where there should be a single truth, and lean into it where each project is rightly its own thing.

## Finding them, and trusting them

None of this helps if people cannot find what exists, so the marketplace is more than a git address the harness can install from, and is published as a browsable catalogue generated straight from the canonical repository. Each skill appears as a card with its description and tags, anyone can filter to the ones relevant to what they are doing, read exactly what each one does, and install it through the harness's built-in plugin manager. Because the catalogue is generated from the source, and a validator checks the structure of every skill, the browsable view never drifts away from the real thing, which is the same single-source discipline that makes the whole collection trustworthy. The website is a view onto the canonical skills rather than a second copy of them that might fall behind.

These skills are internal and open, a `SKILL.md` is just readable Markdown, and anyone can read precisely what a skill will instruct the agent to do before deciding whether to use it, so confidence comes from reading the thing itself rather than from a trust mechanism layered on top. The friction that does exist shows up as churn. When a shared skill keeps getting rewritten, or people quietly disagree about how it should behave, that is an indicator in just the way a much-changed area of a codebase or a hard-fought architecture decision record is, a sign that a conversation needs to happen rather than a problem to route around. Surfacing it, and reaching for a shared skill before reinventing it, is a habit a team builds together through open discussion and pairing rather than through any amount of clever infrastructure.

## Why this one comes last

Looking back over the series, the same single move runs through all of it. A session with an agent is a kind of shared mind built up over an hour or two, and most of what is in it is lost the moment the session ends, or grows large enough that the context fills and the agent starts to fade. Working this way feels a great deal like pairing, and when the pairing stops I can only keep, at best, a partial memory of everything the two of us worked out. So the discipline running under all of it has been to take the parts worth keeping and set them down before they evaporate, while resisting the easier urge to keep everything and bury the repository in well-meaning documents nobody ever reads. [Skills as a By-product of Doing the Work](/notes/skills-as-a-by-product-of-doing-the-work) was about capturing the how, and [Decisions Worth Keeping](/notes/decisions-worth-keeping) about capturing the why, while [Determinism and Useful Ambiguity](/notes/determinism-and-useful-ambiguity) was about knowing which parts should harden into a script, and [Tending the Context](/notes/tending-the-context) about keeping the collection sharp by pruning as readily as adding. Each one turns something that lived only in my head, or only in one session, into something durable.

Distribution comes last because it is the multiplier on all of that. Everything the series has covered so far makes one practitioner steadily better, and a single capable engineer with a well-tuned set of skills is a fine thing, but a whole team of them is a different order of useful. [How I Drive Agentic Software Engineering](/notes/how-i-drive-agentic-software-engineering) opened with Henrik Kniberg's picture of where this is heading, from the horse and cart of coding by hand, to the sports car of one engineer driving a tool like Claude Code, to the spaceship of an agent working as a colleague embedded in the team. Flying my own spaceship is good for me and useful to the company in a modest way. A team where everyone is flying, and sharing the improvements they find as they go, is where the benefit stops being additive and starts to compound, and that is why a personal collection of skills is worth the trouble of handing round. A setup that lives on one laptop reaches no further than one person, whereas the same setup shared is what turns good individual practice into the way a team works.

## Where this leaves us

That closes the arc I set out to write, from driving a single agent through to handing the results round a team. The glimpse ahead, the one Kniberg's [webinar](https://www.abundly.ai/events/2026-06-17/webinar-agentic-engineering-in-practice) pointed at, is of agents autonomous enough to "live" and work alongside the team rather than waiting to be driven. Sharing skills across a team this way is, I think, one of the first real steps towards building that spaceship.
